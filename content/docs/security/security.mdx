GSET is a **transpiler**, not a sandbox. Most of the Go-era security file (size caps, path/command validation around a config loader) died with `gset.conf`. Knowing the seams keeps you safe.

## The honest model

| Concern | Status |
|---------|--------|
| What `gset` runs | Only the target runtime (`go run`) for `gset run`; `gset transpile` only reads a file and prints source. |
| Networking | None in the core. There is no network code in the transpile path. |
| Configuration load | None — no config file is read, so there is no config file to tamper with. |
| Supply chain | The build is Rust; `cargo-deny` checks advisories and licenses in CI. |

## What is NOT protected

- **Your source is arbitrary code in the target language.** Whatever your program transpiles to — file writes, subprocess calls, network access — the target runtime executes with **your user's privileges**. **Run untrusted source like any untrusted program.**
- **No sandboxing, no resource limits, no network policy.** If you need isolation, run GSET inside a VM/container.
- **Generated code is only as typed as the emitter.** Dynamic input can infer to a wrong-but-valid type; the syntax-check gate guarantees *valid* syntax, not *semantically identical* behavior.

## Future hardening

The security surface of the Go version is not being ported. If isolation matters, the honest place for it is the Rust rewrite's `gset run` — running generated code in a container/chroot is on the roadmap (`--sandbox` mode) but is <span className="badge planned">Planned</span>.
