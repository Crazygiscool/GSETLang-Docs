GSET (**Generic Syntax Extension Tool**) is a **single-binary transpiler written in Rust**. It uses [tree-sitter](https://tree-sitter.github.io/) grammars to parse real languages into a shared, typed intermediate representation, then emits a complete runnable file for a target language.

Version: **3.3.2**.

## What GSET actually does

1. **Parses** a source file with a tree-sitter grammar (Python today).
2. **Lowers** it to a typed IR — every node carries a source span and a (possibly `Unknown`) type.
3. **Runs a semantic pass** — lexical scope resolution and conservative type inference.
4. **Emits** a complete file for the target backend (Go today).
5. **Runs** the output with the target's toolchain (`go run`), or prints it with `gset transpile`.

There is no VM. The output is real source code in the target language, executed by the target's own runtime.

## What GSET is today

- **One frontend, one backend, end to end:** Python → Go. This is the M1 milestone, and its gate is that `gset transpile tests/corpus/py/fib.py --to go` emits Go that passes `gofmt` and `go vet`.
- **A typed IR instead of a hand-written AST.** Imports are first-class IR items, backends declare a capability matrix instead of silently dropping constructs, and a `CodeWriter` owns indentation.
- **No configuration file yet.** The Go-era `gset.conf` was deleted. A `gset.toml` is planned (default target, interpreter paths, project root, dependency search roots) but nothing is implemented today.

## What comes next

The [roadmap](/docs/concepts/roadmap) follows the engineering plan in `docs/RUST_REWRITE_PLAN.md`:

- **M2:** JavaScript/TypeScript frontend, all five backends (Go, Python, JavaScript, Java, Ruby), and the corpus-wide syntax-check gate.
- **M3–M5:** more frontends (Go, Java, Ruby, C/C++, Rust), local project graphs, and ecosystem dependency resolution.
- **M6:** cutover — packaging, docs, and the final deletion of the Go tree.
