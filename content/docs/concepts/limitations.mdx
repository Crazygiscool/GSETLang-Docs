GSET is mid-rewrite, and this guide is honest about the seams.

## Language coverage

- **One frontend:** Python. JavaScript/TypeScript land in M2, Go/Java/Ruby/Rust/C in M3.
- **One backend:** Go. Python, JavaScript, Java, and Ruby land in M2.

## Typing

- **Conservative inference.** The semantic pass fills types from literals, annotations, arithmetic, calls, and collection elements; genuinely dynamic code stays `Type::Unknown` and propagates. Wrong-yet-valid output is possible — the syntax-check gate guarantees *valid syntax*, not *identical semantics*.
- **Annotate for typed output.** Unannotated code gets backend-chosen defaults, reported by the `gset-untyped` warning.

## Language features

| Feature | Status | Blocker |
|---------|--------|---------|
| Modular projects | not yet | M4 local project graph |
| Dependency resolution | not yet | M5 (pip, npm, Cargo, Maven, Go modules) |
| Semantic-pair preservation | out of scope | none — by design |
| LSP / IDE integration | out of scope | none — by design |

## Other boundaries

- **One file at a time** for `transpile`/`run`. No project/module orchestration yet (M4).
- **No configuration file.** `gset.toml` is planned, nothing is implemented today.
- **`run` shells to installed runtimes only** for implemented targets (`go` today).

## What GSET deliberately doesn't do

- No VM/interpreter — it always produces real target source and shells to the target runtime.
- No full semantic version solver (out of scope).
- No source-level inlining of compiled/binary dependencies (M5 defines an honest `OpaqueForeign` boundary instead).
